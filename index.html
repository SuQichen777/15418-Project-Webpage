Parallel GPU Hash Tables: Thread Cooperation, Memory Access, and Contention

Jiaxi Zhang (jiaxizha) & Hongzheng Li (hongzhel)

ProposalPDF MilestonePDF Final reportdue Dec 10 PosterDec 11

Summary

We will implement and optimize a concurrent hash table in CUDA that supports parallel insertion, look-up, and potentially deletion or supporting dynamic size. We will explore how collision handling, atomic operations, and GPU memory access patterns affect performance. We will evaluate throughput against CPU and baseline GPU implementations across different table sizes, load factors and key distributions.

Platform
Multicore CPU host and CUDA-capable NVIDIA GPU on GHC
Languages / APIs
C++/CUDA; CUDA atomic operations and cooperative-group primitives
Goals (revised at milestone)
Plan: ≥75% of NVIDIA cuCollections static_map throughput with optimization rungs 1–5 done; fallback ≥60% with rungs 1–2; hope 90–100% with all 7 rungs. See the milestone report.

Optimization ladder

  1. Naive GPU baseline: one thread per operation, 64-bit packed key/value slot, single atomicCAS per claimed slot.
  2. Cooperative probing: a group of G ∈ {2, 4, 8, 16, 32} threads probes an aligned window per step.
  3. Memory layout: vectorized loads and AoS vs. SoA slot storage, evaluated with Nsight Compute DRAM bandwidth and sectors per request.
  4. Contention reduction for skewed or hot-key workloads: intra-warp key deduplication with __match_any_sync and early exit on found keys.
  5. Mixed insert/lookup/delete with tombstones, plus a concurrency stress test.
  6. Stretch: separate chaining with a per-bucket lock-free linked list, compared against linear probing at high load factors.
  7. Stretch: lazy dynamic resizing into a table of twice the capacity once a load-factor threshold is reached.
